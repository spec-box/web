## Технический контекст

- `Home` (`src/pages/Home/Home.tsx`) получает полный список проектов из effector-стора `model.$projects` (`src/model/pages/home.ts`), который заполняется одним запросом `api.projectsList()` без пагинации и поиска на сервере — весь список уже приходит на клиент целиком.
- Текущий `ProjectList` (`src/components/ProjectList/ProjectList.tsx`) сам режет массив на страницы через `Array.slice` и рендерит `Pagination` из `@gravity-ui/uikit`; отрисовку одного элемента делает подкомпонент `Item` (`src/components/ProjectList/components/Item.tsx`), который оборачивает `ListItem` (`src/components/ListItem/ListItem`) и ссылку через `useRouteLink({ to: projectRoute, params: { project: project.code } })`.
- UI построен на Gravity UI (`@gravity-ui/uikit`), стили — BEM через `@bem-react/classname` (`cn(...)`), у каждого компонента свой `.cn.ts` и `.css`.
- В зависимостях уже есть `Drawer` из `@gravity-ui/uikit` (обёртка над `Modal`, поддерживает `placement="right"`, управление через `open`/`onClose`), в проекте он пока нигде не используется.
- Готового переиспользуемого `SearchInput` нет, но есть устоявшийся паттерн поля поиска: `TextInput` из `@gravity-ui/uikit` с `startContent={<Icon data={Magnifier} />}` и `hasClear` (пример: `src/components/TreeFilterPanel/TreeFilterPanel.tsx`); там поиск идёт через effector с debounce для серверного запроса, что здесь не нужно — фильтрация чисто клиентская. Визуальный стиль этого поля (скруглённые края через `--g-border-radius-m`/`-l`, размер/отступы/цвет иконки-лупы) задан прямо в `TreeFilterPanel.css`, отдельного переиспользуемого компонента для него нет.
- Скругление карточек `ListItem` (`border-radius: var(--sb-border-radius-2-xl)`) задано безусловно в `ListItem.css` и наследуется `ProjectItem`, но сама переменная `--sb-border-radius-2-xl` (и остальные `--sb-*` токены: `--sb-font-body-s/-m`, `--sb-font-header-*`, `--sb-font-subheader-*`, `--sb-outline-width`, `--sb-border-radius-3-xl`) объявлена только внутри селектора `.ApplicationLayout` (`src/components/ApplicationLayout/ApplicationLayout.css`), а не на `:root`.
- `.ApplicationLayout` — DOM-узел, который создаёт `ThemeProvider` из `@gravity-ui/uikit` (`scoped rootClassName={bem()}` в `src/components/ApplicationLayout/ApplicationLayout.tsx`); фактические классы узла — `g-root g-root_theme_light ApplicationLayout` (`g-root`/`g-root_theme_*` добавляет сам Gravity через `ROOT_CLASSNAME`). `Modal`/`Drawer` из `@gravity-ui/uikit` монтируют содержимое через `Portal` в `document.body` (хук `usePortalContainer`, дефолтный контейнер — `document.body`; `PortalProvider` с явным контейнером в проекте не используется), то есть DOM-узел портала — не потомок `.ApplicationLayout`. Portal при этом оборачивает содержимое в собственный вложенный `ThemeProvider scoped` (`rootClassName="theme-wrapper"`), который заново применяет классы `g-root g-root_theme_* g-portal__theme-wrapper` — проверено эмпирически (`document.querySelector('.ProjectsDrawer').closest(...)`, цепочка классов предка: `g-root g-root_theme_light g-portal__theme-wrapper`). То есть узел портала снова получает класс `.g-root`, поэтому Gravity-токены (`--g-color-*`, `--g-text-*`, `--g-font-family-sans`), объявленные Gravity через селектор `.g-root`, доступны и там. Наши собственные `--sb-*` токены были объявлены только на `.ApplicationLayout` (селектор по нашему кастомному классу, не по `.g-root`) — этого класса на узле портала нет, поэтому `--sb-*` там не резолвились: отсюда визуально прямые углы карточек и, для шрифтовых токенов, нерезолвящийся `font: var(--sb-font-body-*)`.
- Проверено эмпирически (Chromium/Playwright, `getComputedStyle`): custom-свойство, которое ссылается на другое custom-свойство через `var()` (например, `--sb-font-body-m: var(--g-text-body-font-weight) ... var(--g-text-body-font-family)`), при чтении вычисленного значения на любом элементе резолвится относительно того элемента, на котором это свойство было ОБЪЯВЛЕНО (а не элемента, где оно используется/наследуется). Если объявить `--sb-font-*` на `:root`, а зависимые токены Gravity (`--g-text-*`, `--g-font-family-sans`) при этом объявлены только на `.g-root`-классовом узле (потомке `:root`, а не самом `:root`), то `--sb-font-*` перестаёт резолвиться ВЕЗДЕ в документе, включая `.ApplicationLayout` и всё дерево `Home`/`Project`/`Stat` — не только в портале (это конкретно воспроизведённая причина регрессии шрифтов на главной странице из предыдущей итерации обратной связи). Простые статические custom-свойства без вложенных `var()` (например, `--sb-border-radius-2-xl: 18px`, `--sb-outline-width: 2px`) от этого эффекта не страдают и резолвятся на `:root` корректно.
- Также проверено эмпирически: если вместо `:root` и вместо `.ApplicationLayout` объявить `--sb-font-*` на селекторе `.g-root` (без вложенности в `.ApplicationLayout`), то они резолвятся корректно и на самом `.ApplicationLayout` (у него есть класс `.g-root`), и внутри `Drawer`/`Modal` (у портала при scoped-теме тоже есть класс `.g-root`) — потому что `--g-text-*`/`--g-font-family-sans`, от которых зависят `--sb-font-*`, ТОЖЕ объявлены Gravity именно на `.g-root`, то есть на том же самом узле, а не на его предке.
- Аналогично проверено эмпирически: `Drawer` из `@gravity-ui/uikit` без явного пропа `size` рендерит внутренний фрейм (`.g-drawer__item-content`) со стилевой шириной, равной константе `DRAWER_ITEM_INITIAL_SIZE = 400` (см. `node_modules/@gravity-ui/uikit/build/esm/components/Drawer/constants.js` и `.../components/DrawerItem.js`), независимо от ширины, заданной CSS содержимому внутри `Drawer`. Прежнее значение `width: 400px` в `.ProjectsDrawer` совпадало с этой константой случайно, поэтому переполнения не было заметно; при изменении CSS-ширины содержимого фрейм `Drawer` не следует за ним.
- В проекте нет глобального сброса `box-sizing: border-box` (кроме точечного `box-sizing: border-box` в `FeatureCard.css`); по умолчанию действует `content-box`, поэтому одновременное указание `width` и `padding` у одного блока увеличивает его фактическую отрисованную ширину сверх заданной. Это уже устранено в текущей реализации `ProjectsDrawer.css` через `box-sizing: border-box` и остаётся корректным независимо от несовпадения ширины фрейма `Drawer` с шириной содержимого (см. предыдущий пункт) — это независимая причина переполнения.
- Тестов в проекте нет вообще (ни unit, ни UI), фреймворк тестирования не подключён.

## Ограничения

- Изменение затрагивает только клиент: API `projectsList()` не меняется, весь список проектов по-прежнему приходит одним запросом.
- Поиск в панели — только клиентская фильтрация по уже загрученному массиву проектов (без debounce и без обращения к серверу); это явно предусмотрено для будущей замены на серверный поиск.
- Список внутри панели не виртуализируется (явно вне границ изменения) — обычный скроллящийся `div`.
- Необходимо следовать принятой в проекте структуре компонента (`ComponentName/ComponentName.tsx`, `.cn.ts`, `.css`, `components/` для дочерних частей) и способу подключения effector-моделей через `src/model/pages/*.ts`.

## Решения

### Переиспользование Item и логики рендера проекта

**Решение:**
Существующий `Item` (и его bem-стили `ProjectList-Item`, `ProjectList-ProjectTitle`, `ProjectList-ProjectDescription`) переносится из `ProjectList` в новый общий компонент `src/components/ProjectItem/ProjectItem.tsx` с собственным неймспейсом bem (`ProjectItem`), не зависящим от `ProjectList`. И краткий список на главной, и список в панели используют этот общий компонент.

**Обоснование:**
Верстка и поведение элемента списка (ссылка на проект, заголовок, описание) идентичны в обоих местах; выносить их в общий компонент проще и надёжнее, чем дублировать код рендера проекта в двух местах или тянуть внутренний подкомпонент `ProjectList/components/Item` в новый компонент через относительный импорт мимо публичного API `ProjectList`.

**Рассмотренные альтернативы:**
- Оставить `Item` внутри `ProjectList` и импортировать его напрямую по относительному пути из нового компонента панели — отклонено, так как создаёт скрытую связанность между несвязанными по смыслу компонентами и путает владение стилями (`bem('Item')` использует неймспейс `ProjectList`).
- Продублировать разметку элемента в новом компоненте — отклонено, увеличивает риск рассинхронизации при будущих изменениях карточки проекта.

**Последствия:**
`ProjectList` и новый компонент панели становятся тонкими обёртками вокруг списка `ProjectItem`; `src/components/ProjectList/components/Item.tsx` и его `Item.css` удаляются, `ProjectList.css` лишается стилей `ProjectList-Item`, `ProjectList-ProjectTitle`, `ProjectList-ProjectDescription` (переезжают в `ProjectItem.css`).

### Замена ProjectList на короткий список + кнопку + панель

**Решение:**
`ProjectList` перестаёт заниматься пагинацией и получает новую ответственность — короткий список: рендерит первые 5 элементов из переданного массива (`projects.slice(0, 5)`) через `ProjectItem` и кнопку «Все проекты» (`Button` из `@gravity-ui/uikit`), которая переключает локальный `useState<boolean>` открытия панели. Полный список с поиском выносится в новый компонент `src/components/ProjectsDrawer/ProjectsDrawer.tsx`, который получает тот же массив `projects: Project[]` и флаги `open`/`onClose`, и рендерится рядом с `ProjectList` в `Home.tsx` (или внутри `ProjectList`, см. ниже) через `Drawer` из `@gravity-ui/uikit` с `placement="right"`.

`ProjectsDrawer` держит локальный `useState<string>` для текста поиска и вычисляет отфильтрованный список через `useMemo` по `project.title.toLowerCase().includes(query.toLowerCase())`; список рендерится в прокручиваемом контейнере (`overflow-y: auto`, ограниченная высота через flex-раскладку внутри `Drawer`), без `Pagination`.

Компонент `ProjectList` держит состояние открытия панели и рендерит `ProjectsDrawer` сам (а не `Home.tsx`), чтобы `Home.tsx` не знал о деталях реализации панели и остался тонким контейнером, как сейчас.

**Обоснование:**
Минимизирует изменение публичного контракта: `ProjectList` как принимал, так и принимает только `projects: Project[]`, `Home.tsx` не меняется в части использования `ProjectList`. Инкапсуляция состояния открытия/поиска внутри новых клиентских компонентов не требует изменений в effector-модели `src/model/pages/home.ts`, так как оба списка (краткий и полный) читают один и тот же уже загрученный массив — новых запросов к серверу не требуется.

**Рассмотренные альтернативы:**
- Поднять состояние открытия панели и её рендер в `Home.tsx` — отклонено: `Home.tsx` превращается в менее тонкий контейнер, а `ProjectList` перестаёт быть самодостаточным для повторного использования.
- Управлять открытием и поиском через effector-стор в `model/pages/home.ts` — отклонено как избыточное усложнение: состояние чисто локально-визуальное (открыта/закрыта панель, текст поиска), не требует переживания перезагрузки страницы или синхронизации между несвязанными компонентами, обычный `useState` в React-компоненте — принятый в проекте способ (см. текущий `useState<page>` в `ProjectList`).

**Последствия:**
`ProjectListProps` не меняется. Добавляется новый компонент `ProjectsDrawer` с собственными `.cn.ts`/`.css`. `Pagination` из `@gravity-ui/uikit` в `ProjectList` больше не используется.

### Поле поиска в панели

**Решение:**
Использовать `TextInput` из `@gravity-ui/uikit` с `startContent={<Icon data={Magnifier} />}` и `hasClear` для поиска в `ProjectsDrawer`, без debounce и без effector — значение и обработчик `onUpdate` идут напрямую в локальный `useState` компонента `ProjectsDrawer`.

**Обоснование:**
Debounce в `TreeFilterPanel` нужен там, чтобы не заваливать сервер запросами при вводе, а здесь фильтрация синхронная и локальная — debounce добавил бы только задержку без пользы.

**Рассмотренные альтернативы:**
- Скопировать effector-паттерн `TreeFilterPanel` целиком (стор + `debounce`) — отклонено как избыточное для чисто клиентской синхронной фильтрации; будет пересмотрено, когда поиск станет серверным (вне границ этого изменения).

**Последствия:**
Простая и предсказуемая фильтрация без сетевых эффектов; при переходе на серверный поиск (будущее изменение) потребуется завести effector-стор и debounce по аналогии с `TreeFilterPanel`.

### Общий стиль поля поиска

**Решение:**
Визуальный стиль поля поиска (скруглённые края инпута через локальное переопределение `--g-border-radius-m`/`--g-border-radius-l`, отступы и цвет иконки-лупы) вынести из `TreeFilterPanel.css` в новый общий компонент `src/components/SearchInput/SearchInput.tsx` (+ `.cn.ts`, `.css`), оборачивающий `TextInput` с уже готовым `startContent` (иконка `Magnifier`, опционально `Spin` вместо неё на время загрузки) и `hasClear`. Компонент принимает `value`, `onUpdate`, `placeholder`, необязательный `loading` и `className`. `TreeFilterPanel` и `ProjectsDrawer` используют этот компонент вместо прямого `TextInput`, за счёт чего получают идентичный внешний вид поля поиска без дублирования CSS.

**Обоснование:**
До этого решения в `ProjectsDrawer` стиль поля поиска не совпадал с полем поиска на странице проекта (`TreeFilterPanel`): в частности, не были перенесены переопределение радиуса скругления и стилизация иконки (размер, отступы, цвет `--g-color-text-hint`). Выделение общего компонента устраняет расхождение сейчас и не даёт ему повториться при следующем добавлении поиска где-либо ещё в проекте.

**Рассмотренные альтернативы:**
- Скопировать разметку и CSS поля поиска из `TreeFilterPanel` напрямую в `ProjectsDrawer.css` — отклонено: оставляет дублирование, замеченное сейчас расхождение стилей повторится при будущих правках любого из двух мест.

**Последствия:**
Из `TreeFilterPanel.css` уходят классы `TreeFilterPanel-Title` (сохраняется только `flex`-обёртка при необходимости) и `TreeFilterPanel-SearchIcon`; иконка/`Spin`-индикатор загрузки, которые сейчас специфичны для `TreeFilterPanel` (переключение по `showSpin`), остаются доступны через проп `loading` нового компонента.

### Раскладка панели: переполнение по ширине (устранено)

**Решение:**
В `ProjectsDrawer.css` контейнер `.ProjectsDrawer` получил `box-sizing: border-box` при одновременно заданных `width` и `padding`, чтобы итоговая отрисованная ширина содержимого не превышала ширину, которую резервирует под панель `Drawer`. Это уже сделано в текущей реализации и остаётся в силе.

**Обоснование:**
Без `box-sizing: border-box` `width` и `padding` в CSS проекта (где нет глобального сброса `box-sizing`) складываются, и фактическая ширина блока получается больше заданной — контент вылезает за пределы `Drawer`.

**Рассмотренные альтернативы:**
- Не рассматривались повторно в этой итерации — решение принято и подтверждено в предыдущей итерации обратной связи.

**Последствия:**
Содержимое панели укладывается по ширине в границы `Drawer` без горизонтального переполнения. Это отдельная причина от скругления карточек (см. следующее решение) — обе причины давали похожий внешний симптом «острые/срезанные углы», но независимы друг от друга.

### Скругление и шрифты внутри Drawer: все `--sb-*` токены на `.g-root`, а не на `:root` или `.ApplicationLayout`

**Решение:**
В `ApplicationLayout.css` объявить ВСЕ `--sb-*` токены (`--sb-outline-width`, `--sb-border-radius-2-xl`, `--sb-border-radius-3-xl`, `--sb-font-body-s`, `--sb-font-body-m`, `--sb-font-header-s`, `--sb-font-header-m`, `--sb-font-subheader-s/-m/-l`) на новом селекторе `.g-root` (класс, который сам Gravity добавляет на корневой узел `ThemeProvider`), а не на `.ApplicationLayout` (наш собственный класс) и не на `:root`. `.ApplicationLayout` сохраняет только `--g-color-text-link`/`-hover` и раскладочные свойства (`display`, `flex-direction`, `flex`, `font: var(--sb-font-body-m)`, `color`). Тема-зависимые селекторы `.ApplicationLayout.g-root_theme_light`/`-dark` не трогать.

**Обоснование:**
Предыдущая версия этого решения (перенос только литеральных `--sb-border-radius-*`/`--sb-outline-width` на `:root`, шрифты — оставить на `.ApplicationLayout`) снимала регрессию шрифтов на главной странице, но сознательно оставляла шрифт карточек внутри `Drawer` нерезолвящимся — это и стало основанием блокирующего замечания ревью. Ревью указало на не рассмотренную ранее возможность: `Portal` из `@gravity-ui/uikit` при scoped-теме оборачивает содержимое в собственный `ThemeProvider scoped`, который заново применяет классы `g-root g-root_theme_*` на узле портала (проверено эмпирически — см. «Технический контекст»). Это тот же класс `.g-root`, который уже несёт на себе `.ApplicationLayout`. Объявление `--sb-*` на `.g-root` вместо `.ApplicationLayout` или `:root` работает и на `.ApplicationLayout` (класс `.g-root` там есть), и внутри `Drawer`/`Modal` (класс `.g-root` появляется там же, где и Gravity-токены `--g-text-*`/`--g-font-family-sans`, от которых зависят `--sb-font-*`) — оба используемых в `var()` уровня (наш `--sb-font-*` и Gravity-шный `--g-text-*`) теперь объявлены на одном и том же селекторе, поэтому резолвятся друг относительно друга без дублирования значений. Проверено эмпирически (`getComputedStyle`): шрифты на главной странице (`Inter`, вес/размер как раньше) и шрифт/скругление карточек `ProjectItem`/`ListItem` внутри `Drawer` (`Inter`, `border-radius: 18px`) одновременно корректны при этом решении.

**Рассмотренные альтернативы:**
- Перенести на `:root` весь набор `--sb-*`, включая шрифтовые — отклонено (предыдущая итерация): ломает шрифты везде, где `--sb-font-*` используется, так как `--g-text-*` не объявлены на `:root`.
- Перенести на `:root` только литеральные токены (`--sb-border-radius-*`, `--sb-outline-width`), шрифтовые оставить на `.ApplicationLayout` — это было принятым решением этой же итерации до ревью; отклонено по итогам ревью: оставляет реальный видимый дефект в самой добавляемой функциональности (шрифт карточек внутри `Drawer` — не `Inter`, а браузерный `Times`/serif), хотя решение было в пределах досягаемости (см. ниже).
- Продублировать на `:root` ещё и нужные `--g-text-*`/`--g-font-family-sans`, чтобы шрифтовые `--sb-font-*` можно было безопасно поднять на `:root` — отклонено: решение с `.g-root` достигает того же результата без дублирования значений токенов Gravity и без риска рассинхронизации при обновлении версии `@gravity-ui/uikit`.
- Обернуть `children` в `ApplicationLayout.tsx` в `PortalProvider` из `@gravity-ui/uikit` с контейнером внутри `.ApplicationLayout` — по-прежнему отклонено: то же исправление достигается однострочной заменой селектора в CSS, без изменения точки монтирования порталов всего приложения.

**Последствия:**
Скругление карточек, фокус-аутлайн и шрифт (`Inter`, корректные вес/размер) внутри `Drawer`/`Modal`/любых будущих порталов с scoped-темой работают корректно, без остаточных известных ограничений по этой части. Побочный эффект — тот же класс проблем заранее исправлен для любых будущих компонентов, использующих `Modal`/`Popup`/`Select`/`Tooltip` (все они монтируются через тот же `Portal` с той же scoped-темой).

### Ширина шторки без переполнения

**Решение:**
Передать `Drawer` явный проп `size={460}` (числом, в px) в `ProjectsDrawer.tsx`, а в `ProjectsDrawer.css` заменить фиксированный `width: 400px` контейнера `.ProjectsDrawer` на `width: 100%` (высота остаётся `height: 100%`), чтобы содержимое всегда точно совпадало по ширине с фреймом, который резервирует под себя `Drawer`.

**Обоснование:**
Прямое требование обратной связи — ширина панели должна быть на 15% больше (`400 × 1.15 = 460`). Проверено эмпирически (`getBoundingClientRect` в Chromium): без пропа `size` внутренний фрейм `Drawer` (`.g-drawer__item-content`) жёстко использует библиотечную константу `DRAWER_ITEM_INITIAL_SIZE = 400` независимо от CSS-ширины контента; именно поэтому предыдущее увеличение ширины только в `ProjectsDrawer.css` (`400px` → `460px`) не расширило фрейм и содержимое вылезло на 60px за пределы `Drawer` (видимо и на скриншотах, и в измерении `getBoundingClientRect`). Указание `size={460}` заставляет `Drawer` зарезервировать фрейм ровно нужной ширины; `width: 100%` в `.ProjectsDrawer` убирает дублирование источника истины о ширине (раньше она была одновременно и в `Drawer`, неявно через дефолт, и в CSS) — после фикса ширина панели задаётся один раз, в `size` пропе.

**Рассмотренные альтернативы:**
- Оставить `width: 460px` в `.ProjectsDrawer.css` без пропа `size` — отклонено: эмпирически подтверждённая причина переполнения именно в несовпадении фрейма `Drawer` (400px по умолчанию) и ширины контента; без `size` проблема воспроизводится при любой ширине контента, отличной от 400px.
- Включить `resizable` у `Drawer` вместо фиксированного `size` — отклонено: пользователь просит конкретное увеличение на 15%, а не возможность произвольного ресайза панели, это отдельная функциональность вне текущей обратной связи.

**Последствия:**
Ширина панели — `460px`, содержимое (поле поиска, карточки проектов) не выходит за пределы `Drawer` ни с последующим изменением CSS-ширины контента (единственный источник ширины — проп `size`).

### Выравнивание кнопки «Все проекты»

**Решение:**
В `ProjectList.css` заменить `align-self: flex-start` у `.ProjectList-AllProjects` на выравнивание по центру по горизонтали (`align-self: center`), чтобы кнопка была центрирована так же, как ранее была центрирована `Pagination` (`.ProjectList-Pagination { display: flex; justify-content: center; }`).

**Обоснование:**
Единообразие с прежним расположением элемента управления списком — прямое требование обратной связи; альтернативной функциональной причины держать кнопку у левого края нет.

**Рассмотренные альтернативы:**
- Оставить выравнивание по левому краю — отклонено по прямому замечанию: нарушает визуальную преемственность с прежней пагинацией.

**Последствия:**
Кнопка «Все проекты» центрируется по горизонтали в блоке `ProjectList`, как ранее была центрирована пагинация.

## Стратегия проверки

- Ручная проверка в браузере (через сборку/дев-сервер проекта): на главной странице при более чем 5 проектах видно ровно 5 и кнопку «Все проекты»; открытие кнопки показывает панель справа на всю высоту с полным списком; прокрутка списка в панели работает и не двигает остальную страницу; ввод текста в поиске сужает список по совпадению в названии, а очистка поля возвращает полный список.
- Отдельно проверить визуальные исправления: карточки проектов внутри `Drawer` имеют скруглённые углы со всех сторон, как на главной странице (сверка через инструменты разработчика — `--sb-border-radius-2-xl` резолвится в `18px` на элементе `ListItem` внутри `Drawer`); шрифт карточек внутри `Drawer` — `Inter` (через `getComputedStyle`, `fontFamily` содержит `Inter`), а не браузерный `Times`/serif по умолчанию; поле поиска в `Drawer` визуально идентично полю поиска на странице проекта; ширина панели — `460px`, содержимое не выходит за её пределы.
- Отдельно проверить регрессию, из-за которой возникла предыдущая итерация обратной связи: шрифты на главной странице (заголовок «Проекты», текст карточек, подсказка внизу), странице проекта и статистике визуально и по `getComputedStyle` (`font-family` содержит `Inter`) совпадают с состоянием до правок этого изменения; ширина `Drawer` (`getBoundingClientRect` фрейма `.g-drawer__item-content` и содержимого `.ProjectsDrawer`) совпадает и равна `460px` без переполнения за границу видимой области.
- Убедиться, что `vite.config.ts` не содержит изменений прокси дев-сервера, не относящихся к задачам этого изменения (см. «Риски / Компромиссы»).
- Так как в проекте нет тестовой инфраструктуры, автоматизированных тестов для этого изменения не заводится; проверка контракта — визуальная сверка со сценариями `openspec/changes/home-projects-top5-drawer/specs/home/project-browser/spec.md`.
